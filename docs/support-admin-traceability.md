# Support administrator identity and audit

- Authorization remains in the shared Supabase Auth and server-side allowlist helper. Being the configured notification recipient does not grant support access. Confirm a specific operator by signing into the deployed admin panel as that account and making only an authorized read; never export the allowlist or use a service session as proof of that account's permissions.
- New administrative mutations record the authenticated Supabase user UUID as `admin:<uuid>` in the existing `support_activity.actor` column through the same atomic, service-role-only RPC. The browser cannot provide that identity. The ticket's assigned responsible account remains an independent field with the existing allowlist and filter contract.
- The admin API returns a deterministic pseudonymous display label for new audit actors instead of the raw account UUID. It is for display only, not a role, legal name, or access credential. Existing visitor and email audit entries remain unchanged and are not retroactively linked to accounts.
- Supabase remains the audit source. No schema or permissions change is needed for this slice. A historical message has only an admin/visitor author class; audit events identify who performed a recorded reply, but do not store a durable exact message-to-event foreign key. Also, the current SQL does not record removing an assignee as a separate event. Do not infer links by time or claim that these older gaps were fixed. For a future schema proposal, define explicit event correlation using the operation/request ID and cover unassignment.
- Next: design the intake agent as a separate server principal with its own authorization, explicit human escalation and approved public event sources. Do not classify its actions as an administrator UUID, let it impersonate an operator, or grant it unrestricted service-role access. Require a separate reviewed write contract and provenance before adding automation. This PR does not enable an agent or connect an AI provider.
